    Ask the room — before telling them

    What dominates single-user LLM inference latency on a consumer GPU?
    Decoding reads all weights once per token — generation speed is bandwidth-bound. This is why a 3090 (936 GB/s) beats cards with better FLOPS but less bandwidth.

    tool layer · widgets.js

    Five production tools, one registry

    ToolDeckWhat the audience does with it
    vram01model + quant + context → weights, KV cache and runtime against 24 GB
    ft-est02method + dataset → training VRAM and wall clock on one 3090
    tok-sandbox03types any language → fragmentation and the cost multiplier
    guard-sim04tries to smuggle a prompt past an English/Latin rule set — and gets away with it
    graph-run05runs a swarm: fan-out, verifier failure, bounded retry, human gate

    🧩Same contract

    One function per tool — DeckWidgets["name"] = fn(el, DECK) — written once in the template, named from any slide.

    🧹Self-cleaning

    Long-running tools subscribe to DeckHooks.onSlideChange(), so timers die when the presenter moves on.

    📐Honest scope

    Each tool says on-slide that it is a heuristic: it teaches the shape of a calculation, not a precise number.

    The registry is deck-agnostic: the tool lives in template/widgets.js, the slide only names it. Load order matters — widgets.js before deck.js, because deck.js walks [data-widget] once at boot. Keep tools heuristic-labelled; a calculator that implies false precision invites questions you cannot answer.
