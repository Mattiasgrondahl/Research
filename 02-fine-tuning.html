be honest first

You probably don't need it — and when you do

❌ Don't FT for…

  • Knowledge → use RAG / context
  • One-off style tweaks → prompting
  • "Make it smarter" → bigger model

✅ FT is for…

  • Format reliability (strict JSON, tool calls)
  • Domain voice/style at scale
  • Behavior: refuse-safely, terse answers, your product's policy
  • Small-model distillation of a big one

📊 It really works

  • 7-8B FT'd ≈ GPT-4-class on a narrow task
  • Distillation: 10k synthetic pairs from teacher → cheap specialist
  • Latency & cost: small local model wins
Rule: prompt first, RAG second, fine-tune third — but when it's the right tool, a 3090 is enough. Tonight, not next quarter.
The #1 consultant-grade slide of the talk. FT changes BEHAVIOR (how it answers), not KNOWLEDGE (what it knows) — RAG for facts. Fine-tuning to "teach facts" causes hallucinations via over-fitting. LIMA (arXiv:2305.11206): 1k curated examples matched 52k on style-following.

01
part one

How fine-tuning actually works

Same training as pretraining — same loss — on your examples, with a trick about which weights move.

≈3 min in.
the mechanism

It's just next-token loss, on your words

  • Training = for each token in your answer, nudge weights so the model gives that token more probability.
  • Repeat over epochs (passes through your dataset). Loss ↓ = your style/format more predictable.
  • Full fine-tune moves all 8B weights → needs ~16 bytes/param (weights+grads+Adam) ≈ 128 GB for 8B. Ouch.
  • LoRA: freeze base; train tiny "delta" matrices → 0.3–1% of weights.
  • QLoRA: freeze base in 4-bit + LoRA → an 8B model trains in ~8–12 GB.

the LoRA trick

# a frozen weight matrix W (4096×4096 = 16.7M params)
y = W·x                    # W never changes

# LoRA: learn a low-rank correction
y = W·x + B·A·x            # A: r×4096, B: 4096×r,  r=16
#    trained: 2·16·4096 = 131k params  (0.8%)

# 7B/8B, r=16, all linear layers (q,k,v,o,gate,up,down):
#   ≈ 40–50 M trainable = 0.5% of the model
# AdamW states: 40M × 12 B ≈ 0.5 GB  instead of 96 GB

LoRA arXiv:2106.09685 · QLoRA arXiv:2305.14314

The magic: the update to W during FT is empirically low-rank ("intrinsic dimension", Aghajanyan; LoRA paper). So you can learn 99% of the behavior change with two skinny matrices. QLoRA's NF4 = NormalFloat4: information-theoretically optimal 4-bit for normally-distributed weights + double quantization.

02
part two

Data is 80% of the job

Formats, masking, and the craft that separates a good adapter from a confidently-wrong one.

≈9.5 min in. This section is where projects actually live or die.
the formats

Three dialects, one idea: prompt + answer

sharegpt / openai messages (jsonl)

{"messages": [
  {"role":"system", "content":"You are Acme support."},
  {"role":"user",  "content":"Can I return an opened SSD?"},
  {"role":"assistant", "content":"Yes — within 30 days…
    {\"restock_fee\": 15}"}
]}
# alpaca: {"instruction","input","output"} — legacy but alive
  • Token masking: loss only on assistant tokens — system/user prompts get masked out (TRL: assistant_only_loss=True).
  • Apply the model's chat template before training — mismatched template = gibberish at inference.
  • Keep the system prompt you'll use in production in training examples (or mix a few variants).
  • Hold out 5–10% as an untouched eval set — from day one, not at the end.
Most beginners train on raw prompt+answer without masking — the model then wastes capacity "learning" your prompts and can degrade instruction following. Every framework supports masking; use it.
craft rules

Six rules that beat "more data"

  • 1k curated > 100k scraped — LIMA: 1,000 hand-quality examples matched 52k on instruction quality (arXiv:2305.11206). Noise teaches noise.
  • Diversity over volume per pattern: 30–60 phrasings/contexts per behavior, so the model learns the pattern, not the wording.
  • Consistency: one canonical format everywhere; disagreement between examples = model averages into mush. Audit with a regex/schema pass.
  • Synthetic is fine (and standard): ask GPT-4o/Claude/DeepSeek-R1 to generate + judge your pairs; keep teacher's best 30–50% ("rejection sampling").
  • Keep old skills in the mix: 5–15% general instruction data prevents catastrophic forgetting.
  • Size sanity: behavior change = 500–10k examples. More is for breadth, not depth.
Tell the LIMA war story. Counterpoint (arXiv:2402… "no limits"/diversity studies): data volume does matter for breadth of knowledge tasks — but for behavior/format, curation wins. The 5-15% replay mix is the cheap fix for forgetting.
pipeline · code

From messy logs to training set

# collect → clean → format → mask → split   (the whole loop in 25 lines)
import json, re
rows = [json.loads(l) for l in open("support_logs.jsonl")]

def clean(t):
    t = re.sub(r"https?://\S+", "<url>", t)          # strip links
    t = re.sub(r"\d{3}-\d{2}-\d{4}", "<ssn>", t)      # strip PII — always
    return t.strip()

data = [{"messages":[
    {"role":"system", "content": SYSTEM_PROMPT},          # same as prod!
    {"role":"user", "content": clean(r["q"])},
    {"role":"assistant", "content": clean(r["a"])}]}
    for r in rows
    if len(r["a"]) > 40 and "?" not in r["a"][-2:]     # drop fluff & hedging
    and r["a"] == schema_ok(r["a"])]                    # format gate

shuffle(data); train, evalset = data[400:20000], data[:400]  # eval first!
# TRL: SFTTrainer(train, dataset_text_field="text",
#              sft_config=SFTConfig(assistant_only_loss=True))
pattern used by Unsloth notebooks / TRL SFT docs (local: .research/trl_sft.md).
Emphasize the gates: length filter, schema check, eval-slice carved first, PII scrubbing. The "eval first" trick prevents the classic mistake of leaking train data into eval.
Your FT'd model learned the JSON format but now rambles on everything else. Most likely cause?
Catastrophic forgetting from pure-task training. Mix in 5–15% general instruction/SFT data (or lower LR, fewer epochs, DoRA). More scraped noise makes it worse.
Forgetting is the most common FT complaint. Also mention: over-epochs (1-3 usually) do the same.

first run · code

A real first run — Unsloth in 12 lines

from unsloth import FastLanguageModel
from trl import SFTTrainer, SFTConfig

model, tokenizer = FastLanguageModel.get_peft_model(
    FastLanguageModel.get_model("unsloth/Llama-3.1-8B-Instruct"),
    r = 16, lora_alpha = 16,
    target_modules = ["q_proj","k_proj","v_proj","o_proj",
                      "gate_proj","up_proj","down_proj"],
    lora_dropout = 0)                      # keep it simple

trainer = SFTTrainer(model=model, tokenizer=tokenizer,
    train_dataset=ds, eval_dataset=evalset,
    args=SFTConfig(per_device_train_batch_size=2,
        gradient_accumulation_steps=4, learning_rate=2e-4,
        num_train_epochs=3, optim="paged_adamw_8bit",
        gradient_checkpointing=True, assistant_only_loss=True))
trainer.train()   # → 1-2 h on a 3090 for ~5k examples

Defaults that work

  • r=16, alpha=16, all linear
  • LR 2e-4 (QLoRA), 3 epochs
  • eff. batch 8–16 via accum
  • paged AdamW + grad ckpt
  • watch loss curve, eval on holdout
This runs in a free Colab T4 today; on a 3090 it's ~1-2 h for 5k samples. AI Toolkit equivalent: GUI → pick base → dataset tab → LoRA params → train (same numbers, sliders instead of code). LLaMA-Factory WebUI: llamafactory-cli webui, same fields.

part five

Did it work? Ship it.

Evaluate on the golden set, merge the adapter, serve it — then keep the eval in CI, so the next merge cannot be a silent regression.

Divider for the fifth stop — this is why the agenda has five rows while the HUD previously showed four. Framing for the room: a fine-tune is finished when a number says so, and that number has to be recomputable after every change.
did it work? → ship

Evaluate, merge, serve

  • Loss curves lie. Falling loss on 1k samples ≠ better product. Eval on the holdout.
  • Three-level eval: exact/schema pass-rate on format · win-rate vs base model (LLM-as-judge, blind A/B) · regression check on general prompts.
  • Try checkpoints from each epoch — best is often epoch 1–2, not last.
  • Ship: model.save_pretrained → adapter, or merge_and_unload() → full weights → quantize (llama.cpp / compressed-tensors) → serve on the engine from talk 01.

eval harness sketch

for ex in evalset:
    a = base.chat(ex["user"])
    b = ft.chat(ex["user"])
    score += judge("which follows Acme policy?
        A:{a}  B:{b}  → verdict")
# + json.load(b) must not throw  (schema gate)
# + spot 20 general prompts (forgetting check)
Blind A/B with a judge model is the 30-minute version of real eval. "Best epoch is early" — overtraining shows first in the forgetting check. Merging then GGUF-quants keeps the adapter invisible to the serving stack.

recap

Five things to remember

  • FT changes behavior, not knowledge — RAG first; FT for format, voice, policy.
  • LoRA/QLoRA = 0.5% trainable weights → 8B trains in ~10 GB. Full FT needs ~120 GB+.
  • 1k curated beats 100k scraped; mask non-answer tokens; keep 5–15% replay + a holdout eval set from day one.
  • Engine by style: Unsloth (fast/notebook) · AI Toolkit & LLaMA-Factory (GUI) · TRL/Axolotl (code/config) · verl/OpenRLHF (RL).
  • Time = tokens ÷ ~2–4k tok/s on a 3090: 5k×3ep ≈ 1–2 h. Iterate local, rent A100 for the big run.
