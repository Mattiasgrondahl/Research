Two phases, one bottleneck.

Prefill (time-to-first-token)

Matrix × fat matrix — GPUs are great at it. A 3090 chews ~500–1,500 tok/s of prompt on an 8B model.

Decode (tokens per second)

Each token re-reads all active weights + the whole KV cache once. 936 GB/s ÷ bytes-read = your speed limit.

Community llama.cpp benchmarks on 3090 (llama-bench): 8B Q4 ≈ 600–1,200 t/s pp512, 35–60 t/s tg32.
Key mental model: decode of 1 token reads the whole model from VRAM. So generation tok/s ≈ bandwidth ÷ model bytes, times ~50–60% efficiency. This single fact explains quantization, MoE speed, batching, and speculative decoding all at once.

part two

Weights & quantization

What a "weight" is, and how squeezing them from 16 → 4 bits changed what a 24 GB card can run.

Timer checkpoint 2 — ≈8 min in.
first principles

Weights: 7 billion dials, 2 bytes each

  • A model = billions of floats (the trained parameters). fp16/bf16 = 2 bytes each → 8B params = 16 GB, 70B = 140 GB.
  • Quantization = store each weight in fewer bits, from a shared codebook/scale per group.
  • Q4 ≈ 16× fewer levels per group — enough because weight values cluster tightly.
  • Post-training quant (PTQ): calibrate on a few hundred samples, no retraining — minutes, not weeks.

the whole idea, in fp16 vs Q4

# fp16: exact value per weight
w = 0.022705078125

# 4-bit group quant (group=128):
#   1 scale (fp16) per 128 weights + 4-bit int each
scale = 0.000244   # shared
q     = 93          # w ≈ 93 × scale  (±½ step)

# effective: ~4.5 bits/weight instead of 16
Group-wise asymmetric quant: 128-value group shares a scale (+zero-point), each weight stored as 0-15 integer. Overhead per group ≈ 3 bytes over 128 weights = +0.19 bits → "4-bit" is really ~4.2-4.8 bpw depending on format.

Perplexity is necessary, not sufficient — always run a task eval (lm-eval / your own prompts). Rule of thumb: bigger model at lower bits > smaller model at higher bits. 32B-Q4 beats 14B-Q8 on most tasks.

The single most practical slide: when 24GB is fixed, spend the bits on capacity, not precision — trade 14B-Q8 for 32B-Q4/Q3. "Broken brain at Q2" is literally visible: repetition, broken grammar. Delta ranges are consistent across Llama-2/3, Mistral, Qwen tables.
You have 24 GB and want the best coding assistant that fits. Which weight config wins today?
Capacity beats precision at this scale: 32B-Q4_K_M fits 24 GB (with short context) and beats 7B-Q8 and 13B-Q2 everywhere. 70B-Q4 simply doesn't fit — it offloads to CPU at unusable speed.
Let the room vote first, then click. Common wrong pick is B — "more parameters" at 2-bit is a trap: Q2 quantization destroys more capability than 2× the size adds.

part three

Context & the KV cache

The silent VRAM hog — and why "128k context" has a price on a 3090.

Timer checkpoint 3 — ≈13 min in.
what the KV cache is

Memory for memory: attention's cache

  • Attention re-looks at every past token. Without a cache, each new token recomputes all K/V projections — O(n²) waste.
  • KV cache = stores past Keys & Values per layer, one row per token. Memory grows linearly with context, recomputed on every read.
  • GQA (grouped-query attention): 8B models share KV heads → 8× smaller. MLA (DeepSeek): compresses to one latent → 30–60× smaller.

Do the arithmetic on stage — demystifies everything. 128 KiB/token is THE number for Llama-3-8B. It's why --max-model-len matters and why OOM happens at long context, not short. MLA is why DeepSeek-class models serve 128k affordably.

24GB is shared: 8B Q4 + 128k = 20.9 GB before anything else — one user only. Quantized KV: q8_0 nearly free; q4 saves big but hurts retrieval/needle tasks — cite llama.cpp tests + community. PagedAttention = KV in 16-token pages like virtual memory → near-zero fragmentation, the vLLM unlock.
Your 8B model runs fine at 4k context but OOMs at 16k with 3 concurrent chats. What's the cheapest structural fix?
3 users × 16k × 128 KiB/token ≈ 6 GB of KV on top of weights. Capping context and q8_0 KV (~−50%) recovers it at near-zero quality cost. FP8 hardware doesn't exist on the 3090; buying hardware is never the "cheapest structural fix".
Emphasize: OOM at long context = violet bar, not cyan bar. Diagnose segment, not vibes.

Starter configs that behave on 24 GB

solo — llama.cpp (GGUF)

llama-server -m Qwen2.5-32B-Instruct-Q4_K_M.gguf \
  -ngl 99 -fa on \
  --cache-type-k q8_0 --cache-type-v q8_0 \
  -c 16384 --flash-attn v1 \
  --jinja --port 8080
# OpenAI-compatible API on :8080
# MoE too big? -ngl 99 --n-cpu-moe 24

serving — vLLM / SGLang

# vLLM: 8B AWQ, bounded KV, fp8 off on 3090
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --max-model-len 16384 \
  --gpu-memory-utilization 0.90 \
  --enable-prefix-caching

# SGLang: agent traffic, structured output
python -m sglang.launch_server \
  --model-path Qwen/Qwen2.5-14B-Instruct \
  --mem-fraction-static 0.88 \
  --speculative-algorithm NGRAM # free speedup
Always set max context + memory utilization explicitly — engines reserve KV greedily and OOM later looks mysterious. EXL3/TabbyAPI config is a YAML with quant preset + Q.8 KV. --jinja makes llama-server apply the model's chat template properly.

Real numbers & gotchas

What you'll actually measure on Monday.

Checkpoint 5 — ≈26 min in.
gotchas that bite Ampere users

Six traps

  • No FP8. "FP8 quantization" flags silently fall back or error on sm_86 — stay on INT paths (AWQ/GPTQ/GGUF/EXL3).
  • P2P disabled. 2×3090 tensor-parallel needs the NVLink bridge or --disable-custom-all-reduce; PCIe-only TP works but pays the bus.
  • Context creep. default --max-model-len = model max (128k+) → instant OOM. Set it.
  • KV quant on retrieval. q4 KV passes chat, fails needle-in-haystack — eval before trusting.
  • Quant builds ≠ weights. bad calibration data (GPTQ/AWQ) can wreck one skill silently — spot-check code & math.
  • Power & heat. 350 W card: undervolt to ~280 W, −8% speed, −20% watts; watch the 12VHPWR-era 8-pin adapters.
These are the real forum questions. P2P: NVIDIA disabled it on GeForce drivers; NVLink bridge + modded drivers or just avoid TP with all-reduce. The context-creep trap is #1 first-run failure.
You serve Llama-3.1-8B Q4 in vLLM. Chat works, but with 4 concurrent 30k-token RAG requests it OOMs. The weights are 4.9 GB. Why?
128 KiB/token × 30k ≈ 3.75 GB per stream; four streams ≈ 15 GB — the KV segment ate the card. Fixes: cap context, q8 KV, prefix caching (RAG docs shared!), or fewer max sequences.
Final quiz. RAG twist: shared document prefixes mean SGLang prefix caching or vLLM --enable-prefix-caching collapses much of this — tie back to engine choice.
recap

Five things to remember

  • One equation: 24 GB = weights + KV + ~1.5 GB overhead. Everything else is decoration.
  • Decode is bandwidth: tok/s ≈ 936 GB/s ÷ bytes-read × ~0.55. Quantize weights → speed AND capacity.
  • 4-bit is the sweet spot (Q4_K_M/AWQ/EXL3 4.0, +0.1–0.4 ppl). Bigger-and-quantized beats smaller-and-precise.
  • Context is linear: 8B GQA = 128 KiB/token. Cap it, q8-quantize it, cache prefixes.
  • Engine by workload: solo→llama.cpp/EXL3 · fleet→vLLM · agents/RAG→SGLang · 24 GB can still run 32B dense or 200B+ MoE (offload).
