Control

Instructions in data are not an edge case. They are the design.

Section 1: three slides. Establish that the attack surface is the context window, that the context window now contains other people's content, and that therefore the enforcement point is the request path.
the structural problem

Prompt injection is not a bug you patch — it is what "data" means to a model

2022Term coined, then popularized by Simon Willison: instructions hidden in data. Distinct from jailbreaking, which bypasses the model's own alignment.
2023-02Bing Chat / Copilot manipulated by a web page's hidden text — the first mass-market demo.
2024-11OWASP: adversarial instructions hidden in image pixels — the attack is now multimodal.
2025-02Gemini: instructions in a document written into long-term memory, triggered later via a delayed tool call. Google rated it low.
2025Invisible text shipped in academic papers to steer AI reviewers; AI résumé screeners gamed by applicants.
2025-07Grok-4 jailbroken within ~48h of release: Echo Chamber + Crescendo chained (NeuralTrust).
⚠

Why it escalates

  • The model cannot tell instructions from content — they arrive as one string
  • Add a retrieval step and the string is someone else's text
  • Add a tool and text becomes an action
  • Add credentials and it becomes a data-egress incident
NCSC, Aug 2023, still the best summary of the state of the art: "exercise caution when building off LLMs."
Sources: en.wikipedia.org/wiki/Prompt_injection (accessed 2026-09-05) which cites Nikkei Asia (2025) on AI peer review, NYT (Oct 2025) on résumés, Ars Technica (Feb 2025) on the Gemini delayed-tool-invocation case reported by Johann Rehberger, NeuralTrust (2025-07-11) on Grok-4, OWASP multimodal report (Nov 2024), NCSC guidance (Aug 2023). Structural-defence research exists — StruQ structured queries, USENIX Security '25, pp. 2383–2400 — but nothing yet removes the problem.
what a control plane owes you

Seven questions every request must answer — in order

1 · Who

Key → human → team. No shared keys, no raw provider keys outside the platform team. SSO/OIDC provisions the key.

2 · May they

Model allowlist per key/team, route allowlist, tool & MCP allowlist. Inherited as a ceiling, never as a grant.

3 · Up to how much

max_budget, tpm_limit, rpm_limit, key expiry. This is what stops a runaway agent from minting invoices.

4 · Is this allowed input

Injection/jailbreak/PII scan before the model ever runs.

5 · Was that allowed output

Second scan on the response — plus redact rather than reject for PII, so work still gets done.

6 · Can we prove it later

Append-only log of prompt, retrieved content, tool calls, args, outputs, scores, cost — with a retention policy.

7 · Can we turn it off. A guardrail you cannot disable in one config line will be worked around by whoever needs it off at 2 a.m. Version the policy bundle, keep the previous one, pin model versions, and rehearse the rollback.
This list is derived from what real gateways implement (LiteLLM docs: virtual keys, teams, max_budget/tpm/rpm, model access, allowed_routes, MCP object permissions "inherited as a ceiling", RBAC, IP filtering, audit logs) plus what incidents demand. Question 7 is the one people skip — then someone files an exception and wires around the gateway with a personal API key.

What the chokepoint buys you

  • Routing: fallback, retries, caching, A/B of models behind one endpoint
  • Accounting: cost per key/team/app, exported to your ledger
  • Policy speed: change a YAML, not 40 applications
  • Forensics: one place holding the trajectory

What it costs

  • Latency: +single-digit ms for a local classifier; +a network hop for a vendor API
  • Money: free if self-hosted, or per screened token ($0.10/1M at Model Armor)
  • Availability: it is now on your critical path — run 2 replicas, health-check providers, keep a break-glass key
  • 政治: someone must own the policy. Unowned gateways decay into allow-everything
The agent runtime hangs off the same gateway but adds its own rails: tool allowlist, human-in-the-loop gate, trajectory log, sandbox. Mention the operational reality: the gateway becomes load-bearing, so treat it like your auth service — signed images, pinned release tag, migration job, two replicas. LiteLLM publishes cosign-verified -stable images and Terraform modules for AWS/GCP exactly for this.

the primitive that does the work

A virtual key is a policy object — this is the whole control plane in 14 lines

POST /key/generate
{
  "key_alias":      "payments-team",
  "team_id":        "t-pay",
  "user_id":        "sso:u_4471",        # OIDC/JWT → key
  "models":         ["gpt-5.5", "kimi-k2.5"],   # allowlist
  "max_budget":     250,                 # hard stop, $
  "tpm_limit":      80000,
  "rpm_limit":      600,
  "duration":       "30d",               # expires: no zombie keys
  "allowed_routes": ["chat", "embed"],   # not /model/new
  "object_permission": {
    "mcp_access_groups": ["jira-read"]   # ceiling, never a grant
  }
}
shape: LiteLLM proxy virtual-key API (docs.litellm.ai, accessed 2026-09-05)

Why each line matters

  • models kills shadow AI: no frontier model on a personal card
  • max_budget is the only thing that stops an agent loop spending real money
  • allowed_routes: management access follows the owner's role — an admin-owned key can call admin APIs unless you scope it
  • spend lands in queryable tables → your finance export; teams own keys, humans inherit them
Verbatim behaviours from the virtual-keys docs: model access and MCP access are always evaluated against the key row; management-route access follows the owner's role, which is why allowed_routes exists for every role including admin-owned keys; MCP entitlements are inherited as ceilings. If your gateway cannot answer "what did team X spend and which tools could they call", it is a router, not a control plane.

WithSecure's SPIKEE benchmark (Jan 2025): a top-10 reasoning model placed 17th of 19 on prompt-injection resistance in isolation. Two different leaderboards, two very different models.

What to do with that

  • Benchmark the guardrail, not the vendor's marketing: run your own attack set on your own traffic
  • Guardrail scores are on held-out taxonomies, not on your policy text — re-measure after you write your policy
  • A cheaper router target (deck 07) can be a safety decision, not only a cost one: swap-in models need re-testing
  • Keep the eval set versioned next to the prompt: model swaps are deploys
SPIKEE result reported by Infosecurity Magazine (Jan 2025), cited via the prompt-injection article: R1 17th of 19 in isolation, 16th with rules/marker strategies, while ranking 6th on Chatbot Arena at the same time. Also worth saying: jailbreaks keep landing on frontier models within days of release, so "we use a safe model" is not a control. securing agents

Give the agent its own identity, a ceiling of tools, and a human on the irreversible ones

🪪

Identity

  • Its own principal: workload identity / service account, never a human's token
  • Short-lived credentials; scoped to the minimum tool set
  • Gateway enforces the ceiling: an over-privileged owner cannot leak privilege into a key
🧰

Tools & MCP

  • Deny-by-default allowlist per agent key; group servers by risk, not by convenience
  • Pin & diff tool definitions; treat every tool response as untrusted input
  • NeMo's execution rails intercept tool input and output — the last place a human rule can still apply
✋

Human gate

  • By risk tier: reads free · writes confirm · money/credentials/deletion require approval
  • Log the whole trajectory: prompt, retrieved content, calls + args, outputs, scores
  • Sandbox the blast radius: separate account, no default creds, egress allowlist, per-agent quota

An agent holding a jira-read MCP group reads a poisoned ticket and follows its instructions. What actually contained the damage?
Input guards look at prompts; the payload arrived as a tool result. Alignment is not a control you can audit. And logging is a detector, not a stopper — it tells you what happened afterwards. The only thing that reliably bounded this is the scope written into the key before the incident.
This is OWASP Agentic Top-10 ASI06 — excessive agency, the one item from that list I could cite directly. Your gateway has Shieldstral on input and output, and a strong PII redactor. An agent with send_email is tricked by a webpage into mailing a customer list. Which control was missing?
The content was legitimate — no injection in the model's own output, no PII rule violated in text. The failure is excessive agency: the agent should not have had an unmonitored send capability. Guards buy time; least privilege buys safety.

guardrails as a pipeline, not a poster

If it isn't in CI, it rotted six weeks ago

# .ci/guardrails.yml  — the four gates
gate_1_attack_set:        # 300 prompts: direct + indirect + encoded + CJK + low-res
  run: redteam-suite --policy policy-bundle/v14 --fail-on-asr 2%
gate_2_over_refusal:      # the other failure mode
  run: xstest-suite --fail-on false_refusal 5%
gate_3_contract:          # tool args, JSON schema, PII regex, banned topics
  run: guardrails validate --schema tools.json --pii
gate_4_replay:            # yesterday's incidents, forever
  run: replay --tickets SEC-118,SEC-131,SEC-144 --must-block all

# model / policy swap = deploy. pin everything.
model:  kimi-k2.5@2026-07-15      # never "latest"
policy: policy-bundle/v14        # previous bundle stays deployable
rollback: gateway --policy v13   # one line, rehearsed quarterly

The four gates

  • Attack set: block regressions, with a stated ASR budget
  • Over-refusal: measure it in the same run or safety becomes theatre
  • Contract: tool args + schema + PII, cheap and boring
  • Replay: every real incident becomes a permanent test — this is how you stop re-losing the same fight
Rollback rehearsal is a quarterly drill: flip the policy bundle, confirm the previous one still loads, confirm the break-glass path is logged.
This is deck 04's red-teaming methodology reduced to YAML. The point of showing it here: guardrail owners usually own the runtime and nobody owns the regression test, so policy drift is invisible. ASR budget (2%) and over-refusal budget (5%) are illustrative thresholds — set them per org and write down why.

recap

Five things to remember

  • Own the chokepoint. One base URL, one key per team, budgets and model/tool allowlists on the key — that is where control physically lives.
  • Injection is structural. Data and instructions share one channel, so quarantine content and treat every retrieved or tool-returned string as untrusted.
  • Guards are cheap, auditors are not. 86M classifier ≈ free (ASR 17.6% → 7.5%); reasoning auditor → 2.89% but utility −4.6pt and a second generation per checked step. Order them cheap-first, apply the expensive one after sensitive tool calls.
  • Price the scan. Cloud guards bill screened tokens ($0.10/1M) — at 800M tokens/day that's ~$2.4k/mo for a 3B model you can run yourself under an Apache-2.0 licence.
  • Version it, test it, rehearse the off switch. Attack set + over-refusal + replay in CI, pinned model versions, one-line rollback drilled quarterly.
