part one

Tokens: the unit of everything

Models don't see text. They see token IDs — and that choice has economics.

≈1.5 min in.
how vocabularies get built

Three algorithms, same trick

BPE

Start from characters, merge the most frequent pairs until vocab N. GPT-2/3/4 (tiktoken), Llama 2/3.

WordPiece

Like BPE but merges by likelihood gain, adds ##. BERT family.

Unigram

Start huge, prune by loss; probabilistic segmentation. SentencePiece → T5, Gemma, Llama-1.

  • Byte-level base (GPT-2, Llama-3): any character representable — no <unk> death spirals
  • The vocab race: GPT-2 50k → GPT-4 100k → Llama-3 128,256 · Qwen2.5 151,643 · Gemma 256,000 · GPT-4o 200k
  • Bigger vocab = fewer tokens for CJK/morphology, but bigger embedding tables + rarer (worse-trained) tokens
All three converge: frequency-weighted subword compression of a corpus. Vocab sizes from model cards/tiktoken registry. The Tokenizer Paradox (arXiv:2402.06787): bigger vocab isn't monotonically better — rare tokens under-train.

the byte-level rebellion

What if we skipped tokenization?

  • Mamba char models — plain bytes in, no vocab.
  • BLT — Byte Latent Transformer (Meta, arXiv:2412.09871): dynamic byte patches chosen by local entropy; Pareto-beats BPE models at same FLOPs; language-agnostic by construction.
  • NexusAI Flash (2025): byte-based edge model — "end of tokenization" marketing.

Why BPE still wins (for now)

  • bytes = 2–4× longer sequences → attention & KV cost explodes
  • tokenizer is one-time; a bad one taxes forever
  • Hybrid/adaptive patching is the likely middle path
Practical rule: check the tokenizer before blaming the model — multilingual quality complaints often end at vocabulary, not weights.
Byte-level models also dodge the "tokenizer mismatch" mess in model families (Llama-2→3 changed vocab; caches/templates broke). Watch adaptive-patching (BLT) as the research frontier.
A Japanese support bot on GPT-3.5 (cl100k) costs ~2.5× the English equivalent per conversation. Cheapest structural fix?
Tokenizer choice is a deployment decision. o200k cut Japanese ~30%+ vs cl100k; Qwen/Gemma (151k/256k) are CJK-friendlier. Quantization (D) changes memory, not token counts.
Quiz. The "physics" trap is tempting — but vocab choice halves the tax with zero model retraining.

part two

Speculative decoding

Guess several tokens, verify in one pass. The 2–6× speed lever — and a whole family of "who guesses".

≈10 min in. Callback to Talk 01: decode is bandwidth-bound; compute idles → let something cheap fill it with guesses.
the core trick

Draft → verify → keep the prefix you like

  • Draft model proposes γ next tokens (cheap).
  • Target model checks them in one parallel pass (the slack compute).
  • Accept the longest matching prefix, reject the rest — with rejection sampling, output is mathematically identical to the target alone. Lossless.
  • Speedup ≈ (1−α^{γ+1}) / ((1−α)(γc+1)) — α=accept rate, c=draft cost ratio.
  • α ≈ 0.7–0.8, γ 4–8 → 2–3.6× typical; the game is maximizing α per extra GB.

one decode step, speculative

target so far: "The capital of France is"
draft proposes:  " Paris" " in" " Europe"

target verifies all 3 in one forward pass:
  " Paris"  ✓ accept
  " in"     ✗ reject → stop here
  (" Europe" skipped; bonus token sampled)

→ 2+ real tokens for the price of 1 pass

Leviathan et al. arXiv:2211.17192; Chen et al. 2302.01318

Stress "lossless": temperature and all, distribution-preserving — spec decode is free correctness-wise, which is why every engine shipped it. The draft source is the design axis → next slide family tree.

ngram · the free lunch

Drafting from the future's memory

  • Keep a suffix structure (hash/automaton) of everything in context; when generating, look up the last n tokens, propose whatever followed them last time.
  • Cost: microseconds on CPU. Zero weights, zero VRAM.
  • Wins when output copies input: RAG answers, summarization, agents re-emitting tool output, code completion, JSON boilerplate, user repeats themselves.
  • Useless on novel prose (α≈0) — and there it costs nothing. REST (arXiv:2311.08252) extends the draft source to an external corpus.

python -m sglang.launch_server \

  --speculative-algorithm NGRAM \

MTP · trained-in prediction

Multi-token prediction: a head for tomorrow, today

  • Pretrain with extra prediction targets: besides t+1, also t+2… → tiny extra module learns to look ahead.
  • DeepSeek-V3: one sequential MTP module beyond the backbone; auxiliary loss λ=0.3 also improves the main head; used speculatively at ~90% acceptance → +1.8× throughput (paper).
  • Now shipping in: DeepSeek-V3/R1, Gemma-3n, Qwen3-Next, several 2025-26 open models — the "draft included in the weights" trend.
  • Bonus: MTP training signal = richer gradient → better data efficiency (Meta's MTP work, arXiv:2404.19737: up to 3× on coding/math).

MTP vs EAGLE: MTP trained WITH the model (weight synergy, no extra download, fixed depth 1); EAGLE added AFTER training (any model, tunable depth/tree). SGLang numbers: Llama-3.1-8B MT-Bench on H100: 158 → EAGLE-2 244 → EAGLE-3 373 tok/s (docs). DeepSeek: 1.8× at ~90% accept.
2026 frontier

DFlash → DFlash 2 → DSpark: diffusion drafts

  • DFlash (arXiv:2602.06036, z-lab): a tiny block-diffusion draft model — unrolls a whole 16-token block in one parallel pass, conditioned on target hidden states.
  • Where EAGLE autoregresses its draft (7 sequential micro-steps), DFlash emits the block at once → accepted length up, wall-clock draft cost down → >4× class speedups reported on Qwen3/Gemma class models.
  • DFlash 2 (inco.ai, HF z-lab): upgraded system; first ckpts: Muse-Glimmer-30B, Qwen3.8-27B.
  • DSpark (DeepSeek, arXiv:2607.05147, DeepSpec repo): block-7 drafts trained against cached target outputs; official EAGLE-3 / DFlash / DSpark checkpoint triplets for Qwen3-4/8/14B + Gemma-4-12B; eval suite: gsm8k…arena-hard-v2 acceptance.

Why it matters on a 3090

  • draft = ~1–2.5 GB on top — fits where 70B doesn't
  • one-shot blocks = less kernel-launch churn (consumer GPUs love it)
  • SGLang: --speculative-algorithm DFLASH --speculative-draft-model-path …
  • tradeoff: needs pp_size=1, no dp-attention, overlap off (docs)

sources: local .scratch/dflash_readme.md, dspark_readme.md; SGLang spec-decode docs.

Diffsusion drafting = the "MLLM moment" for spec decode: non-autoregressive drafters got good enough that parallel block proposals beat autoregressive drafting end-to-end. DSpark is DeepSeek's take + open training stack (DeepSpec) — note the 38 TB target-cache warning, this is serious infra.
Your agent framework re-sends the same 8k system+tools context on every step and echoes large chunks of tool JSON into its answer. Which draft source gives the best speedup-per-GB?
Copy-heavy workloads are ngram's home turf: α stays high because drafts are retrieved from the context itself — at 0 extra GB and 0 extra weights. EAGLE/DFlash then add on top for the novel parts.
Ties to the agent-swarm talk: ngram is why agent traffic benefits disproportionately. Modern stacks mix: ngram for retrieval stretches + model-based draft elsewhere.

moe × tokens × speed

How the three layers of this talk interlock

  • MoE + tokens: fewer active params per token × fewer tokens (better tokenizer) = the two multiplicative ways to make inference cheap.
  • MoE + drafting: cheap decode leaves more headroom for verification — DFlash/EAGLE acceptance gains are larger on MoE serving (DeepSeek's own stack uses MTP + MLA).
  • MLA (DeepSeek's compressed KV): ~70 KB/token — MoE's storage-side partner; dense attention models pay 2–20× more per token.
  • Training tax: MoE needs load-balancing tricks, is less stable to fine-tune (expert drift), and 4-bit quantized MoE has more per-expert error to manage — the price of the cheat code.
This slide earns the deck's title "the token stack". End with it: efficiency is multiplicative across all three layers; the frontier (DeepSeek line) pushes all three at once.
Why can a single 24 GB RTX 3090 generate from Qwen3-30B-A3B at ~25–40 tok/s but barely runs Qwen2.5-32B (dense, same size) at ~10–15?
Generation speed ≈ bandwidth ÷ bytes-read; MoE reads a ~3B-parameter slice per token. (KV is per-layer full-width though — MoE doesn't shrink attention, that's MLA's job.)

recap

Five things to remember

  • Tokens are an economic choice — vocab race (50k→256k) cut multilingual taxes; always check the tokenizer before blaming the model.
  • Spec decode is lossless free speed: draft-then-verify; the game is α (acceptance) per extra GB.
  • Four drafters: ngram (0 GB, copy-god) · MTP (trained-in head, ~90% α) · EAGLE-3 (best general) · DFlash/DSpark (parallel diffusion blocks, >4×).
  • MoE = quality on a bandwidth diet: 9–30× active/total ratio; VRAM still needs the whole model — offload or MLA to fit.
  • The frontier is multiplicative: tokenizer × drafting × MoE(+MLA) — efficiency stacks.
