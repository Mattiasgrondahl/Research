Why it matters to you

  • The official ComfyUI template has two UNET loaders and two samplers — you can retarget each with its own LoRA
  • Style LoRAs mostly belong on the high-noise expert; detail LoRAs on the other
  • ai-toolkit can alternate between experts every N steps (switch_boundary_every: 10) to save memory
  • Hosted products hide all of this behind one button; the graph shows it
Mixture-of-experts, diffusion flavour: ~27B parameters total, ~14B active per step. That is why a 14B "active" model needs the memory of a 27B one — both experts have to live somewhere.
Sources: Wan 2.2 README (MoE high-noise/low-noise design, ~27B total / 14B active) and the official ComfyUI template JSON (2× UNETLoader, 2× KSamplerAdvanced, ComfySwitchNode). switch_boundary_every is from ai-toolkit's train_lora_wan22_14b_24gb.yaml. This is the single best "aha" for a mixed audience — the model isn't one thing.

Speed

Every accelerator in this space exploits the same three things.

Section 3: the estimator widget and the principles behind the speedups. Keep this brisk — the widget is the star.
live demo · will it run, and how long

Set your box, set your shot. The estimate is honest about itself

How to drive it: (1) leave Wan 2.2 14B on the 4090 — it lands on the measured anchor, say so out loud ("this cell is a real run, not a model"); (2) turn the 4-step LoRA on → ~97 s; (3) drop to an 8 GB card → it stops fitting, and the fix line tells you to quantize; (4) quantize to GGUF Q4 → it fits again but the time estimate grows, because the speed/fit tradeoff is real; (5) push frames to 121 and watch VRAM rise while a WanGP-style offload would keep it flat — that's the next section. Anything off an anchor is an extrapolation by a pixel×frame scaling law; the readout says so every render.
what the accelerators exploit

Three levers, and a fourth you should not skip

🧮

Fewer steps

  • Step-distillation LoRAs: 4–12 steps instead of 20–50
  • Cache tricks skip whole steps: TeaCache, MagCache (1.7× at 20 steps), TaylorSeer, FasterCache
  • Adapters now ship per model: lightx2v/*-Stepwise-Lightning, Helios (CVPR 2026)
🪶

Less memory

  • int8 / fp8 / GGUF / NVFP4 / NF4 / Nunchaku 4-bit
  • Quantized KV cache + offload instead of buying a card
  • WanGP: VRAM independent of clip length via aggressive offload
🧩

Cheaper math

  • Sparse attention: SSTA — "up to 36× compression" pipeline in Hunyuan 1.5
  • GGUF CUDA kernels +15% video, ×3 GGUF LLM (vendor)
  • Tiled VAE decode so 1080p doesn't spike memory
The fourth lever is not an accelerator: generate small and upscale. 640×640 then RIFE + FlashVSR / Lanczos. The Wan 2.2 x1.5/x2 upsampler is itself an official ComfyUI template at ≈12 GB. Speed you buy by not rendering pixels you were never going to keep.
Sources: HunyuanVideo-1.5 card (SSTA, MagCache 1.7× at 20 steps, 4-step distill −75%), lightx2v adapter family, Helios CVPR 2026, FastVideo (UC Berkeley), WanGP docs (quant list, +15%/×3 CUDA kernels, offload), ComfyUI upscale workflow templates (wan22_i2v_14B_upsampler_x1.5 / _x2). Caveat worth saying: distillation and cache-skipping trade fidelity for speed, and the papers' "no accuracy loss" claims are theirs — check motion coherence on your own clips.

ComfyUI & WanGP

The graph is the interface. Two tools, two philosophies.

Section 4: what a workflow actually is (and the API-format trick that makes it automatable), the anatomy of the official Wan 2.2 template, then WanGP as the accessibility layer.
what a workflow actually is

A ComfyUI workflow is a dataflow graph — which is why you can automate it

# the template file is a DAG; "API format" is the JSON the UI posts
POST http://127.0.0.1:8188/prompt
{
  "prompt": { "1": {"class_type": "CheckpointLoaderSimple", ...},
              "7": {"class_type": "KSampler", "inputs": {...}} },
  "client_id": "<ws-uuid>"          # progress + execution_error over /ws
}
GET /prompt                 # still-queued work
GET /prompt/pending         # capacity before POSTing (avoid 500s)
GET /history/{prompt_id}    # outputs after exec_success
GET /view?filename=…&type=output

# partial execution: queue only the output node you care about
#   → renders a preview without paying for the video encode
#   → and never overwrites the file the last run produced
ComfyUI backend-guide · frontend ≥1.24.x for partial execution, ≥1.24.3 for subgraphs

Two formats, one graph

  • Save format: node titles, positions, colours — for humans
  • API format: numeric IDs, no layout — for code
  • Every speed/memory decision is a node you can change: sampler, sigmas, quantization, VAE tiling
  • ComfyUI-Manager for install/update; comfy-cli generate/list/schema for automation
  • Runs on Python 3.13, cu130, Ascend NPU, Cambricon MLU, Apple Silicon, ROCm 7.2
Sources: ComfyUI docs — backend-guide/api-endpoints (POST /prompt, client_id, /history/{prompt_id}, GET /view, pending capacity to avoid 500s), backend-guide/execution ("executing only up to that node and not running the full workflow" for partial execution; output-node conflict warnings), nodes/Progressive-execution, CHANGELOG 1.24.3 (Subgraph Template Library). The platform list is from the installation docs. Say the automation line for the business people: "this is why you can put it behind an API and a queue".

Why it belongs in an enterprise conversation

  • It turns existing hardware into an inference fleet: workstation leftovers, gaming rigs, AMD cards

Training a video LoRA

ai-toolkit, a folder of clips, and the failure mode nobody warns you about.

Section 5 is the practical core: the config, the dataset, burn-in, the checkpoint ladder, then the closing quiz/poll/recap.
ai-toolkit in one screen

A 14B video LoRA on one 24 GB card: 4-bit weights plus a recovery adapter

# config/examples/train_lora_wan22_14b_24gb.yaml  (official example)
model:
  name_or_path: "ai-toolkit/Wan2.2-T2V-A14B-Diffusers-bf16"
  arch: 'wan22_14b'
  quantize: true
  qtype: "uint4|ostris/accuracy_recovery_adapters/…uint4.safetensors"
  low_vram: true
  train_high_noise: true   # both experts, or pick one
  train_low_noise:  true
network: {type: lora, linear: 32, linear_alpha: 32}
datasets:
  - folder_path: "/path/to/video/folder"
    caption_ext: txt
    caption_dropout_rate: 0.05      # never 0
    num_frames: 1                   # frames, not clips — see next
    resolution: [512, 768, 1024]
train:
  steps: 2000                       # "500 - 4000 is a good range"
  switch_boundary_every: 10         # alternate experts, save memory
save:  {dtype: float16, save_every: 250, max_step_saves_to_keep: 4}

What to say about each knob

  • uint4 + recovery adapter is what puts a 14B on one card
  • train_text_encoder: false — shipped comment: "probably won't work with wan"
  • Samples render at num_frames: 1 — you review stills, not videos
  • GUI on localhost:8675, or python run.py cfg.yaml
The image-first Wan 2.1 example still says "we will train on 1 frame at a time" — video LoRAs here are mostly trained on frames.
Config is the official example, fetched from ostris/ai-toolkit (saved as .scratch/src_video/kit_cfg_wan22_14b_24gb.yaml). The recovery adapters live at huggingface.co/ostris/accuracy_recovery_adapters. The FLUX minimum in the toolkit FAQ is "24GB of VRAM for a standard LoRA", and the same FAQ says you do not need to crop or resize images — the toolkit buckets aspect ratios. Wan 2.1 example: resolution [632], train_on_first_frame: true, comment "AI-Toolkit does not currently support video datasets". Two config traps worth naming if asked: cache_text_embeddings and unload_text_encoder are mutually exclusive (the toolkit raises and tells you), and quantize: false with skip_ref_load is the documented escape from load-time OOM.
the dataset is the hard part

20–60 clips, 2–6 seconds each, captioned like you mean it

The caption rule that saves you

Caption everything you want to be able to change — camera, lighting, background, motion — and keep the trigger word for the thing you want locked. Burn-in is mostly the model having nothing left to attribute to context.

Dataset tools in the toolkit

  • only_if_contains / ignore_if_contains — split datasets by caption without moving files
  • Sample generation every 250 steps; eval_every for a held-out set
  • low_vram: true trades speed for fitting; quantize: false + skip_ref_load if you hit load-time OOM
Lengths and counts: ai-toolkit official Wan 2.2 example (20 videos referenced in comments), WanGP dataset guide ("at least 8–10 seconds, multiple angles" for its own workflows), community video-LoRA guides. The 8k+1 rule follows Wan's VAE temporal compression (4× in 2.2, 16×16×4 in TI2V-5B). Label this section honestly as practitioner consensus plus the config's hard constraints — there is no paper that settles "how many clips".
burn-in: the failure mode

Burn-in is the LoRA leaking into everything — and each cause has a switch

SymptomUsual causeWhat you change
Every generated person becomes your subjectidentity over-binding: too many steps / too high strengthstrength 0.4–0.6 → adopt the earliest checkpoint that works → cut steps 2000 → 800–1200
Concept drags its background / lighting alongcaptions never described background, so the trigger absorbed itre-caption with camera, lighting, scene · caption_dropout_rate 0.1
Plastic, oversaturated, high-contrast lookover-training on a turbo base model — the canonical Turbo symptomlower LoRA strength; train on the non-turbo base and add the speed LoRA at inference; de-turbo stabilizer (ostris/Z-Image-De-Turbo)
Style bleeds into other promptsrank too high for a small datasetlinear: 32 → 8–16 · target fewer layers · LoKr with lokr_full_rank: true

Motion freezes / jittersframes-only training with too few real motion examplesmore clips containing the motion · keep num_frames > 1 where VRAM allows · check the 8k+1 rule

Checkpoint-ladder protocol — the actual fix

save_every: 250, keep 8+. Test 500 / 750 / 1000 / 1500 at strengths 0.4 / 0.6 / 0.8 on the same 10 prompts (5 "pure concept", 5 "concept in new contexts"). Adopt the earliest rung that captures it. That one sentence removes ~80% of burn-in grief.

Two things that are not cures

  • More steps. Burn-in is over-attribution, and steps buy more of it
  • Regenerating from the same prompt. You are sampling the same bias — use the ladder
Provenance, stated out loud: "burn-in" is practitioner vocabulary. I found no paper, no ai-toolkit FAQ entry, no WanGP docs page defining it — the community term for a related failure is "identity/character drift". The ostris/Z-Image-De-Turbo stabilizer, the "lower strength on Turbo models" advice, and LoRA weight-strength sweeps are documented; the causal table above is my synthesis of documented mechanisms plus community practice. Label it as such on stage — it's the most challenged slide in the deck.
Your video LoRA works beautifully on 5 test prompts but every unrelated prompt now shows your subject. Fastest correct fix?
Over-binding is a strength and schedule problem, so fix it with strength, the checkpoint ladder, and captions that leave attributes for context to explain. More steps make it worse, and a full fine-tune is strictly harder to control and impossible to mix.
Reinforces the ladder. If they ask "what strength should I ship?": the answer is "the number your 10-prompt test produced", written in the model card next to the LoRA, because it travels with the checkpoint.

recap

Five things to remember

  • 6 GB is the new floor. WanGP and HunyuanVideo-1.5 put open video on GTX-10-class and AMD cards; quantization, not param count, decides if it runs.
  • A distillation LoRA is the cheapest speed there is: 536 s → 97 s on the same 4090 with the same weights.
  • ComfyUI is a graph, not an app: API-format JSON + POST /prompt + partial execution means it automates — and every speed/memory choice is a node you can see.
  • Wan 2.2 is two experts, and there is no official Wan 2.5. Know which model you're actually quoting.
  • Video LoRAs die of schedule and dataset, not VRAM. 20–60 clips, 8k+1 frames, captions that name every variable attribute — then take the earliest checkpoint on the ladder that works.
